# Scenario 3 — Database connection incident and pooling

Following an increase in API replicas, users intermittently receive
connection timeouts. The database endpoint is reachable, and the incident
began during a deployment. Diagnose whether the timeout occurs in the
application pool, network, pooler, or the database itself. Restore service
with a scoped mitigation, then route a canary through the supplied pooler
and show recovery under the same load.

## (a) Existing resources

- **Database**: the same Postgres cluster from scenario 1
  (`interview-db-app` secret in `cnpg-database`). Your app from scenario 1
  (or the scenario 2 baseline) should already be deployed against it.
- **Connection budget**: a restricted database role, `loadtest`, with a
  connection limit of 80. This is separate from the database's own global
  connection limit and from your app's own `appuser` role — it exists to
  bound this exercise's synthetic load so it can't exhaust the whole
  instance.
- **A pooler**: `interview-db-pooler`, a PgBouncer instance in
  `cnpg-database` namespace, port 5432, transaction pooling mode. Your
  canary can point at it instead of the database directly.
- **Diagnostic access**: a superuser connection exists
  (`interview-db-superuser` secret, `cnpg-database` namespace) for
  inspecting `pg_stat_activity` and related system views — interviewer/
  admin use, ask if you need a connection run on your behalf.
- **Scripts**: `interview/prereq/3/scripts/leak-connections.sh` (opens N
  connections under the `loadtest` role, holds them for a duration) and
  `synthetic-client.sh` (continuous HTTP client, logs timestamp/status/
  latency to CSV). Both need a `kubectl port-forward` to reach in-cluster
  services from this workstation — cluster-internal DNS names
  (`*.svc.cluster.local` or short service names) aren't resolvable
  directly from here.
- Your app's connection pool size is configurable via the `PG_POOL_MAX`
  environment variable (`apps/api/src/db.js`), default 10.

## (b) Scenario tasks

1. Start `synthetic-client.sh` against your deployed app as a baseline
   (confirm all-success before doing anything disruptive).
2. Simulate the incident: scale your app's replicas up and/or increase
   `PG_POOL_MAX`, and run `leak-connections.sh` against the `loadtest`
   role to add synthetic load.
3. Diagnose the failure mode using `pg_stat_activity` (grouped by
   `usename`/`state`/`wait_event_type`), transaction age, and
   `pg_blocking_pids` — distinguish app-side pool wait from a database-
   side rejection from a network-level timeout.
4. Apply a scoped mitigation (not a blanket fix) to restore service.
5. Calculate a connection budget across your app's replicas, the pooler's
   configuration, and the 80-connection role limit.
6. Cut a canary of your app over to the pooler (`interview-db-pooler`
   instead of the database directly), with a sane `PG_POOL_MAX`, and show
   `synthetic-client.sh` recovering to all-success under the same load.
7. Clean up: stop the synthetic load, confirm the `loadtest` role's
   connections return to zero.

## (c) Final outputs and proof of completion

- `synthetic-client.sh`'s CSV log, showing the failure window and the
  recovery after your fix.
- The `pg_stat_activity`-based evidence you used to identify the root
  cause (query output, screenshots, or notes).
- Your calculated connection budget (replicas × pool size × pooler
  capacity vs. the 80-connection limit).
- Confirmation the `loadtest` role has zero active connections after
  cleanup: `SELECT count(*) FROM pg_stat_activity WHERE usename =
  'loadtest';` should return `0`.
- Be ready to discuss what would NOT be safe about simply raising the
  connection limit instead.
