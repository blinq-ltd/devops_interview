# Scenario 1 — Ship an application safely

You have a frontend/API repository, an EKS cluster provisioned with
Terraform, ECR, and a private database. Containerize and deploy the app.
Commit a Dockerfile, one Helm chart or Kustomize overlay, and a minimal CI
workflow. Show a successful request that persists data and reads it back.

## (a) Existing resources

- **EKS cluster**: `interview` (Kubernetes 1.36), reachable via `kubectl`
  from this workstation (already configured).
- **ECR repository**: `382163918348.dkr.ecr.us-east-1.amazonaws.com/devops-interview-api`
  — push your built image here.
- **Database**: a Postgres cluster reachable in-cluster. Credentials are in
  a Kubernetes Secret named `interview-db-app` in namespace
  `cnpg-database`, with keys `user`, `password`, `host`, `port`, `dbname`,
  `uri`. Wire it into your Deployment however you see fit (env var, volume,
  etc.) — it needs to be in the same namespace you deploy into, or copied
  there.
- **Application source**: `apps/api/` in this repository. Node.js/Express,
  `GET/POST/PUT /items`, `GET /livez`, `GET /readyz` (checks DB
  connectivity), and a documented migration command (`npm run migrate`,
  `apps/api/src/migrate.js`, applies `apps/api/migrations/*.sql`). No
  Dockerfile, chart/overlay, or CI workflow exists yet — that's your task.
- **Your access**: the workstation's IAM role can push/pull the ECR
  repository above and has `kubectl` access to the `interview` cluster.

## (b) Scenario tasks

1. Write a Dockerfile for `apps/api` (multi-stage, non-root, reasonable
   image size).
2. Build and push the image to the ECR repository above.
3. Write a Kubernetes manifest, Helm chart, or Kustomize overlay that
   deploys the app with the database wired in, plus resource
   requests/limits and liveness/readiness probes.
4. Apply the schema migration against the database (your choice of
   mechanism).
5. Deploy the app to the `interview` cluster.
6. Write a minimal CI workflow (GitHub Actions is the default choice,
   matching this org's tooling) that builds and pushes the image. Show
   your intended authentication approach even if you can't run a hosted
   workflow in this environment.
7. Demonstrate a request that writes data (`POST /items`) and a
   subsequent request that reads it back (`GET /items`).

## (c) Final outputs and proof of completion

- The Dockerfile, deployment manifest/chart, and CI workflow file, all
  committed.
- `kubectl get pods` showing your Deployment's pods in a `Ready` state.
- Output of a `POST /items` call followed by a `GET /items` (or
  `GET /items/:id`) call showing the posted data was persisted and read
  back — from `kubectl exec curl`, `kubectl port-forward` + local `curl`,
  or equivalent.
- Be ready to walk through: how secrets reach the running pod, IAM/OIDC
  trust design for the CI workflow, and the request path from a client to
  the database.
