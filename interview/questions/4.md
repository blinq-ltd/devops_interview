# Scenario 4 — Central observability, loss and cardinality

Grafana must let us correlate logs and metrics for our services. In this
lab, diagnose a sudden series increase and change the collector
configuration to stop the unnecessary cardinality. Then block telemetry
delivery briefly, restore it, and show what was retained, replayed, or
lost.

## (a) Existing resources

- **Grafana**: `http://<this-workstation's-public-IP>:3000`. Admin
  password: `kubectl --namespace observability get secrets
  kube-prometheus-stack-grafana -o jsonpath="{.data.admin-password}" |
  base64 -d`.
- **Prometheus**: `http://<this-workstation's-public-IP>:9090`, already a
  Grafana datasource.
- **Loki**: already a Grafana datasource (`loki-gateway` service in
  `observability`).
- **Alloy**: the collector, `observability` namespace, release name
  `alloy`. Its configuration is a Helm-managed ConfigMap
  (`kubectl get cm alloy -n observability -o yaml` to inspect). The source
  file is `interview/prereq/4/alloy-config.alloy` in this repo — edit it
  and apply via:
  ```
  helm upgrade alloy grafana/alloy --version 1.13.1 -n observability \
    -f interview/prereq/4/alloy-values.yaml \
    --set-file alloy.configMap.content=interview/prereq/4/alloy-config.alloy
  kubectl rollout restart deployment/alloy -n observability
  ```
  (ConfigMap changes don't auto-restart the pod.)
- **A request generator**: `synthetic-generator` Deployment in
  `observability`, continuously making requests and exposing Prometheus
  metrics on its own `:9090/metrics`, plus structured logs.

## (b) Scenario tasks

1. In Grafana/Prometheus, find the metric with an unexpectedly growing
   series count coming from the `synthetic-generator` job. Identify which
   label is responsible.
2. Edit `alloy-config.alloy`'s relabeling configuration to drop that
   label before it reaches Prometheus, and apply the change (see above).
3. Show the series count has stopped growing.
4. Show you can still identify a specific request after the fix — the
   identifying value is present somewhere other than the metric; find
   where, and demonstrate correlating a specific request across that
   signal and the metrics.
5. Scale `alloy` to 0 replicas for roughly 5 minutes (the generator keeps
   running and logging throughout), then scale back to 1. Separately
   account for what happened to metrics vs. logs during that window.
6. Apply a `NetworkPolicy` blocking Alloy's egress to Prometheus/Loki (not
   `kubectl scale` this time — Alloy itself must keep running and keep
   trying to send) for about a minute, then remove it. Show whether the
   data from that window was retained and eventually delivered, or lost.
7. Sketch (verbally or in a diagram) where you'd draw trust/network
   boundaries if this collector were shipping data to a centralized
   backend in a separate AWS account.

## (c) Final outputs and proof of completion

- A PromQL query and screenshot/output showing the series count for the
  affected metric before your fix (growing) and after (flat).
- The edited `alloy-config.alloy`, committed.
- Evidence of the correlation in (b)(4) — e.g. a specific identifying
  value found in one signal and matched to the same request's metric
  data point by timestamp.
- For the Alloy-stopped exercise: what you observed in Grafana/Prometheus
  for the outage window (a gap vs. no gap), and for logs, whether the
  outage-window log lines eventually appeared in Loki after Alloy
  restarted.
- For the NetworkPolicy exercise: evidence (query results, dashboard,
  Alloy's own internal metrics) that queued data drained after the policy
  was removed, or evidence that it didn't — either is a valid finding if
  you can explain why.
