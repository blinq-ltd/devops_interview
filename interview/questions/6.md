# Scenario 6 — Terraform drift, EKS maintenance and scaling

Review a proposed Terraform change for the existing EKS cluster. Explain
exactly what will change, and revise the configuration to avoid an
unintended replacement. Then demonstrate a safe, small application rollout
while a synthetic client runs, and give your sequence for a later EKS/node
upgrade.

## (a) Existing resources

- **Terraform code**: `infra/eks/` in this repository, managing the
  `interview` EKS cluster, its VPC, and node group. Backend state is in S3
  (see `infra/eks/provider.tf` for the exact bucket/key).
- **Your access**: an IAM role, `candidate` (assumed by your `gleb` IAM
  user), scoped to run `terraform plan`/`apply`/`destroy` against
  `infra/workstation` and `infra/eks`. See `infra/candidate-access/README.md`
  for how to configure your AWS CLI profile to use it.
- **The proposed change**: `interview/prereq/6/proposed-change.tfvars`, a
  modified version of the current `infra/eks/terraform.tfvars`
  (snapshotted at `interview/prereq/6/candidate-starting.tfvars` for
  reference). A `terraform plan` against the proposed change has already
  been run and saved to `interview/prereq/6/saved-plan.txt` for a fast
  first look.
- Your scenario 1/2 application should already be deployed to the
  cluster — you'll use it for the rollout demonstration.

## (b) Scenario tasks

1. Read `interview/prereq/6/saved-plan.txt` (or run your own
   `terraform plan -var-file=interview/prereq/6/proposed-change.tfvars`
   from `infra/eks/`). Identify every resource that changes, which ones
   are safe, and which one(s) force a replacement — and explain exactly
   why, in AWS/Terraform terms.
2. Revise the configuration so the safe part(s) of the change can be
   applied without triggering the unintended/disruptive replacement.
   Explain the approach you'd take instead if the disruptive goal is
   still something the business wants.
3. Apply only the safe, revised part of the change against the real
   cluster, and show a clean `terraform plan` afterward (no unexpected
   diff).
4. Start a synthetic client against your deployed application (reuse
   `interview/prereq/3/scripts/synthetic-client.sh` if convenient, pointed
   at your app).
5. Demonstrate one safe, small rollout of your application (e.g. a
   replica count change, or a new image tag) while the synthetic client
   keeps running, with zero dropped requests.
6. Describe your sequence for a later EKS control-plane and node version
   upgrade (you are not expected to perform one live) — version
   compatibility, add-on compatibility, spare capacity, workload
   readiness/PDBs, worker replacement order, validation, and what's
   actually recoverable if something goes wrong.

## (c) Final outputs and proof of completion

- A written (or verbal, recorded in notes) explanation of exactly which
  resources in the proposed plan change vs. replace, and why.
- Your revised Terraform configuration/tfvars, applied, with a `terraform
  plan` showing no further changes afterward.
- The synthetic client's log/output spanning your rollout, showing no
  failed requests.
- Your upgrade sequence, as a concrete ordered list with the compatibility
  and rollback caveats you'd actually check before each step.
