# Scenario 6 — Terraform drift, EKS maintenance and scaling

A change to this EKS cluster's Terraform configuration has been proposed
and planned, but not applied. Part of what it does is wanted; at least one
part of the resulting plan is not something you'd want to run against a
live cluster without a closer look.

**Ideal end state**: the configuration reflects only the change you've
decided is safe to make now, applied against the real cluster with a clean
plan afterward, and a small live rollout of your application completes
with zero dropped requests while that configuration is in effect. You're
also able to lay out, concretely, how you'd approach a future EKS
control-plane and node version upgrade on this cluster.

## (a) Existing resources

- **Terraform code**: `infra/eks/` in this repository, managing the
  `interview` EKS cluster, its VPC, and node group. Backend state is in S3
  (see `infra/eks/provider.tf` for the exact bucket/key).
- **Your access**: an IAM role, `candidate` (assumed by your `gleb` IAM
  user), scoped to run `terraform plan`/`apply`/`destroy` against
  `infra/workstation` and `infra/eks`. See `infra/candidate-access/README.md`
  for how to configure your AWS CLI profile to use it.
- **The proposed change**: `interview/prereq/6/proposed-change.tfvars`, a
  modified version of the current `infra/eks/terraform.tfvars`
  (snapshotted at `interview/prereq/6/candidate-starting.tfvars` for
  reference). A `terraform plan` against the proposed change has already
  been run and saved to `interview/prereq/6/saved-plan.txt`.
- Your scenario 1/2 application should already be deployed to the
  cluster, and `interview/prereq/3/scripts/synthetic-client.sh` is
  available if you want continuous traffic against it.

## (b) Scenario tasks

Work out what the proposed change actually does to the running cluster,
which parts of it you're comfortable applying as-is and which aren't, and
get the configuration to the state you've decided is correct. Then show
that an application rollout stays safe under that configuration while
traffic is flowing. Separately, be ready to walk through how you'd
approach upgrading this cluster's control plane and nodes to a newer
version.

## (c) Final outputs and proof of completion

- Your explanation of what the originally proposed plan would have done,
  resource by resource.
- The Terraform configuration you ended up applying, and a `terraform
  plan` showing no further changes afterward.
- A log or recording of a live application rollout with continuous
  traffic running against it, showing no failed requests.
- Your upgrade approach for this cluster, as something concrete enough to
  actually follow — not just a list of considerations.
