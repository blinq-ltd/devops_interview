# Scenario 2 — Argo CD reconciliation and safe migrations

The service is now managed by Argo CD. A release is degraded after a
configuration change. Diagnose it, repair its Git source, and prove Argo
reconciles to a healthy application. Add a migration Job that must succeed
before the new API version rolls out. Demonstrate that a deliberately
failing migration prevents that release.

## (a) Existing resources

- **Argo CD** is installed in the `argocd` namespace. Get the admin
  password: `kubectl -n argocd get secret argocd-initial-admin-secret -o
  jsonpath='{.data.password}' | base64 -d`. Reach the UI via
  `kubectl port-forward -n argocd svc/argocd-server 8080:443`, or
  `https://<this-workstation's-public-IP>:8080` directly.
- **An Application**, `devops-interview-api`, in project
  `devops-interview`, syncing from this repository's
  `interview/prereq/2/gitops/` path (branch `main`) into namespace
  `interview-baseline`. Check its current status:
  `kubectl get application devops-interview-api -n argocd`.
- **A migration Job skeleton**:
  `interview/prereq/2/migration-job-skeleton.yaml` — a starting point, not
  wired into the sync path yet.
- The Deployment's image, database connection, and the AppProject/
  Application definitions are all under `interview/prereq/2/`.

## (b) Scenario tasks

1. Inspect the Application's current sync and health status. Diagnose why
   it's not healthy (pod events, logs, and the rendered manifest vs. live
   object are all available to you).
2. Fix the root cause in Git (`interview/prereq/2/gitops/deployment.yaml`
   or wherever the problem actually is), and show Argo reconciling to a
   healthy state — either via auto-sync or `argocd app sync`.
3. Incorporate a migration Job (you can start from
   `migration-job-skeleton.yaml`) so it runs before a new release rolls
   out, exactly once, with sane cleanup/retry behavior. Explain your
   choice of mechanism.
4. On a throwaway branch or overlay, make the migration deliberately fail
   (e.g. invalid SQL), sync it, and show that the application release is
   blocked while existing pods remain available. Then revert.
5. Be ready to discuss: how you'd separate dev/staging/prod permissions
   for this setup, and what happens if someone hotfixes a running pod
   directly with `kubectl` while Argo's auto-sync is on.

## (c) Final outputs and proof of completion

- The Git commit(s) that fixed the degraded release, and the Application
  showing `Synced`/`Healthy` afterward (`kubectl get application
  devops-interview-api -n argocd` or the UI).
- The migration Job's manifest, committed, with your chosen
  ordering/safety mechanism visible in it (e.g. a hook annotation, a
  separate pipeline step — your call, justify it).
- Evidence of the failing-migration demonstration: the Job's failure
  output, and confirmation the application release did not proceed (e.g.
  `kubectl get application` still showing the previous healthy revision,
  or `kubectl rollout status` never completing) — plus confirmation you
  reverted the throwaway branch/overlay afterward.
